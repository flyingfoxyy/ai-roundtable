# Table —— 多 AI 圆桌辩论工具 · 设计文档

日期：2026-08-15
状态：已定稿（经用户确认；协议部分吸收了 codex/gpt-5.6-sol 的评审意见）

## 1. 目标

给定一个纯文本议题，让多个异构 AI CLI（claude / codex / gemini）进行结构化的对抗性讨论，
产出一份**各方都明确表态接受的方案**；无法达成共识时，如实输出候选方案、未决分歧与各方立场。

**非目标（v1 明确不做）**：
- 代码库相关议题（AI 不访问文件）
- Web 界面、token 级流式输出
- 断点续跑（`--resume`）
- 动态主持人（LLM 决定发言顺序）
- 讨论记录摘要压缩（仅做简单截断保护）

## 2. 需求约束

- 纯文本议题：方案设计、技术选型类，靠推理讨论，不需要工具
- 自动运行 + 用户可随时插话介入
- Python ≥ 3.11（需要 tomllib），仅标准库，零第三方依赖
- 实验性小工具：简单优先，但协议语义必须严格

## 3. 形态与产物

```bash
python table.py "微服务还是单体：5人团队的新电商项目怎么选？" --max-rounds 5
```

终端实时打印各方发言（ANSI 颜色区分；按调用完成顺序打印，落盘按规范顺序）。
每次运行产出：

```
runs/20260815-1432-微服务还是单体/
├── transcript.md   # 完整讨论记录，每条发言完成后立即追加落盘
├── state.json      # 协议状态快照（版本、票、约束），每次事件后原子重写
├── session.jsonl   # 审计日志：每次调用的命令、耗时、退出码、重试、stderr 摘要
└── final.md        # 结果文档（见 §7）
```

目录名中的议题 slug 经过清洗：仅保留 `[\w一-鿿-]`，截断至 40 字符，防 `/`、`..`、超长。

## 4. 参与者与适配层

内置默认三名参与者（零配置可跑）；存在 `table.toml` 时覆盖：

```toml
[[participants]]
name = "Claude"
cmd = ["claude", "-p"]            # prompt 一律走 stdin，回复取 stdout
lens = "重点审查：可维护性与长期复杂度"
timeout = 300                      # 秒，可选，默认 300

[[participants]]
name = "Codex"
cmd = ["codex", "exec", "--skip-git-repo-check", "-"]
lens = "重点审查：工程落地成本与迁移风险"

[[participants]]
name = "Gemini"
cmd = ["gemini"]                  # 非 TTY stdin 即进入非交互模式；各 CLI 的确切参数以启动预检验证为准
lens = "重点审查：性能、扩展性与运维负担"
```

设计决策：
- **lens（审查侧重）而非 persona（扮演人设）**。评审指出人设会诱导模型为扮演角色而编造分歧；
  分派互补的审查视角在认识论上更干净，异构模型本身的分歧照常保留。
- **进程隔离**：所有 CLI 调用的 cwd 设为 `runs/<id>/sandbox/`（空目录），避免 CLI 读取当前项目、
  留下提示注入产生副作用的入口。各 CLI 的工具禁用参数在 `table.toml` 注释中给出建议值，不硬编码。
- **进程管理**：`subprocess` 以 `start_new_session=True` 启动；超时用 `os.killpg` 杀整个进程组，
  防止 CLI 的子进程残留。超时/失败重试一次。
- **启动预检**：正式讨论前对每个 CLI 发一条 60s 超时的 ping prompt（要求回复 PONG），
  验证认证与可用性，失败则带清晰报错中止（`--skip-preflight` 可跳过）。

## 5. 讨论协议（核心）

标准委员会模式：独立提案 → 轮值主编合成 → 并行盲审 → 主编修订，循环至共识或轮数上限。

```
阶段0  独立立论：全体并行、互相不可见，各自提交分析+完整方案 → 消除首稿锚定
阶段1  合成：主编 P0 汇总各方案为 v1，附明确的「分歧点清单」
循环（第 k 个评审周期，k = 1..max-rounds）：
  盲审：当前版本作者之外的全体参与者【并行】评审，
        产出：公开论述 + 表态 ACCEPT / BLOCK
        - 同周期内互相看不见对方的发言与票（并行即盲），历史周期全部公开
        - BLOCK 必须一次列全所有问题，并分级：[硬伤] / [偏好] / [待验证]
        - ACCEPT 必须附「残余风险声明」：当前方案最强的反例/失败边界，
          以及为何这些剩余分歧可以容忍——"感觉合理"不构成 ACCEPT
        - 第 1 周期的 ACCEPT 必须逐条回应 v1 的分歧点清单
  判定：全体评审者 ACCEPT
        → 版本作者对该版本原文做最后确认投票（生成 ≠ 审查过，作者也必须投票）
        → 作者 ACCEPT ⇒ 共识达成，散会
        → 作者 BLOCK 自己的版本 ⇒ 其意见并入 blocker，继续循环
        零 BLOCK 但存在缺票（失败/INVALID）
        → 版本未变，已有票保持有效；下一周期仅向缺票者补征表态
        存在 BLOCK
        → 下一位轮值主编汇总全部 blocker，产出 v(n+1) + 变更清单 + 逐条处理说明
          （采纳 / 部分采纳 / 拒绝并说明理由）
终止  达到 max-rounds 仍无共识 → 按 §7 输出 NO_CONSENSUS 结果
```

**共识的严格定义（协议不变量）**：

> CONSENSUS(v) 成立，当且仅当：每一位配置的参与者都有一条绑定到版本 v（草案文本的
> sha256 前 8 位 + 版本号）的有效 ACCEPT；所有票产生于 v 创建之后；不存在更新的版本；
> 投票之后没有新的人类插话。任何新版本产生即作废全部旧票（包括作者的）。
> 任何参与者因失败/INVALID 缺票 → 该周期不可能达成共识；终局仍缺票 → 结果标记 INCOMPLETE，
> 绝不把缺席、跳过或解析失败静默计为同意。

**角色轮转**：author(v1)=P0；author(v(j+1)) = 序列中 author(v(j)) 的下一位。每版评审者 = 除作者外全体。

**诚实性框架**：工具能证明的只是"这些无状态调用对这段确切文本返回了 ACCEPT"，
不证明方案正确，也不证明模型有稳定立场。final.md 与文档措辞遵守这一边界。

**调用成本**：N=3、max-rounds=5 时，最坏约 3+1+5×3+1 = 20 次调用；阶段0与评审批次内部并行执行，墙钟时间明显低于纯串行。

## 6. 人类插话

- 主循环在**每个批次/调用的边界**非阻塞检查 stdin。讨论进行中随时按 Enter，
  当前批次完成后暂停，出现 `你说: ` 提示；空回车 = 继续。
- **语义：人类输入是最高优先级的绑定约束**，不是普通参与者的一票。编号为 H1, H2, …
  持续显示在此后所有 prompt 中。
- 插话立即作废当前周期已收集的票；当前轮值主编必须在下一版的变更清单中逐条回应人类约束。
  插话触发的新版本进入下一个评审周期，正常计入 max-rounds（成本阀门语义不变）。
- `/stop`：当前批次结束后跳过剩余周期，直接进入 §7 终局输出。
- Ctrl-C：优雅退出；transcript / state / audit 本就即时落盘，无数据丢失。

## 7. 输出与终局

**final.md 两种结局**：

- **CONSENSUS**：最终方案 = 被投票的那个版本的**原文**（hash 标注，禁止任何事后润色），
  附：完整表态记录（谁、对哪个 hash、何时）、各方 ACCEPT 时的残余风险声明汇总、
  以及「共同盲区与外部验证建议」——三个模型可能共享同一种错误知识，模型共识 ≠ 事实正确。
- **NO_CONSENSUS / INCOMPLETE**：当前候选版本原文 + 仍然有效的全部 blocker（按分级）+
  各方最后立场摘要 + 一份**明确标注「主编个人建议，未经全员认可」**的推荐方案附录
  （保证无共识时用户仍有可行动的产出，但绝不冒充共识）。

## 8. 输出格式与解析

各角色输出以固定标记行分段（标记行独占一行，允许首尾空白，除此之外严格匹配）：

```
阶段0：  <分析>            ---PROPOSAL---  <完整方案>
评审：   <公开论述>        ---VERDICT---   ACCEPT <残余风险声明> | BLOCK <分级问题列表>
主编：   <回应说明>        ---DRAFT---     <完整新版草案>
                           ---CHANGELOG--- <逐条 blocker 处理说明>
确认票： <审查意见>        ---VERDICT---   ACCEPT | BLOCK ...
```

解析策略（评审意见：宽松正则会掩盖协议错误）：
1. 严格解析，失败 → **一次格式纠错重试**（把原输出与格式要求发回，要求重发完整回复）；
2. 仍失败 → 记 **INVALID**：发言原文进 transcript 存档，但不产生任何投票效力，
   该参与者本周期缺票（后果见 §5 不变量）。绝不猜测语义。

## 9. 上下文构造

每次调用无状态，prompt 全量拼装，按序包含：

1. 圆桌规则说明 + 本参与者身份与 lens
2. 议题 + 人类约束列表（H1…Hn，标注绑定性）
3. 当前版本全文 + 版本号/hash + 上一版变更清单
4. 已公开的讨论记录（按周期顺序；进行中周期的并行发言互不可见）
5. 本次任务指令 + 输出格式约定

**截断保护**：拼装超过 `--max-context-chars`（默认 120,000 字符）时，从最早的周期开始丢弃
发言正文（保留一行占位「第 k 周期讨论已省略」），议题、人类约束、当前版本、变更清单永不丢弃。
不做 LLM 摘要。

**隐私与成本提示**（文档与 README 声明）：议题与全部讨论记录会发送给三家模型供应商；
全量拼装使累计输入 token 随轮数近似平方增长，max-rounds 是主要的成本阀门。

## 10. 代码结构

评审意见采纳：不强求单文件，但保持最小结构——纯逻辑与 IO 分离：

```
table.py            # 入口：argparse、主循环、终端交互(插话/颜色)、子进程适配、落盘
table_protocol.py   # 纯逻辑（无任何 IO）：协议状态机、版本与投票账本、共识判定、
                    # 输出解析、prompt 拼装 —— 可独立导入测试
table.toml          # 可选的参与者配置
tests/
  test_protocol.py  # 纯逻辑单元测试
  test_integration.py + fake_cli.sh   # 假 CLI 集成测试
```

## 11. 错误处理汇总

| 故障 | 处理 |
|---|---|
| CLI 调用超时/非零退出 | 杀进程组 → 重试一次 → 仍败：评审者按缺票处理；主编失败则轮转下一位代任（记入审计） |
| 输出解析失败 | 一次格式纠错重试 → INVALID 缺票，原文存档 |
| 参与者终局仍缺票 | 结果标记 INCOMPLETE，不静默降级 |
| 进程崩溃/强杀 | transcript/state/audit 均为事件级即时落盘，数据不丢（续跑功能留待后续） |
| 议题含危险字符 | slug 清洗（§3） |
| 同分钟重名 | 目录名含时分 + 冲突时追加序号 |

## 12. 测试策略

**纯逻辑单元测试**（test_protocol.py，含评审补充的用例）：
- 解析：各角色格式的正确/变体/缺标记 → INVALID 路径
- 状态机：新版本作废全部旧票（含作者票）；混合版本的票永不构成共识；
  插话作废本周期票；缺票 → INCOMPLETE；零 BLOCK → 作者确认 → CONSENSUS；
  作者 BLOCK 自己版本的路径；轮转规则
- prompt 拼装与截断保护；slug 清洗

**集成测试**（假 CLI，不烧 token）：
- `fake_cli.sh` 按脚本吐预设输出 → 驱动完整快乐路径（阶段0 → 共识）
- 超时路径：假 CLI 挂起 → 断言整个进程组被杀干净
- 落盘：中途 kill -9 编排器 → 断言已有事件完整落盘

**真实冒烟**：3 CLI、小议题、`--max-rounds 2` 跑通一次。
